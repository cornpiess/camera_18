# Camera18 相机响应校准

## 2026-10-28 v5与ProRAW候选对比

本分支七种风格使用 `camera18-srgb-ci-v2`，ORIG仍直通。v2先做有界细边缘与影调，再做编码sRGB域luma锚定的颜色cube及有限保护。旧v1配方保留历史顺序，不静默升级。新tone中性轴取自旧CPU近似，细节和保护强度属于审美初值，均为approximation；没有实拍配对或盲比结果，不能宣传已测还原度或画质改善。

`self-test`现同时覆盖新旧传递函数、颜色cube锚定、预览／成片一致性、细节边界、场景限制与固定诊断容量。必须在macOS实际运行；Linux静态检查不替代它。`probes`关闭颗粒、暗角、细节与场景适应，仅测固定颜色／影调响应；完整render才包含全部配方处理。CPU参考仍只作为护栏，不作为CI像素证据。

ProRAW只在离线工具里比较，不进入默认App采集。macOS12+使用同一profile对处理图与RAW分别渲染：

```bash
bash scripts/native-calibration.sh render \
  assets/camera-profiles.json mf50 modules/camera-engine/ios/LUTs \
  controlled-heif.heic heif-result.png final
bash scripts/native-calibration.sh render-raw \
  assets/camera-profiles.json mf50 modules/camera-engine/ios/LUTs \
  controlled-proraw.dng raw-result.png final
```

render-raw通过CIRAWFilter检查控制支持，sharpnessAmount设为0.15、localToneMapAmount设为0.2（仅在支持时），extendedDynamicRangeAmount=0。其他显影参数服从解码器默认；这不是未经处理的线性RAW。输出记录实际decoder、属性支持与值、原生输出尺寸、场景上下文和总时间。使用当前系统实际解码器，不硬编码RAW9符号或假设可用。两张PNG按相同观看尺寸比较，处理耗时仍须在iPhone上验收；桌面结果不能证明移动端采集、光圈和内存兼容。

旧 `fit` 命令生成的候选仍为v1的完整RGB响应（其拟合包括明暗），不得把colorContract标签改成v2直接使用，否则会被新cube的luma锚定改变。它可作为保留的校准工作流，不自动覆盖v2生产配方。`evaluate`可核验renderer5的v1或v2原生probes报告；v2完整样片需同时检查有界保护与空间细节。

## 历史v4交付与边界

2026-10-27：八种内置模式均不再添加人工颗粒。色彩、影调、deharsh 与暗角在预览／成片共享；颗粒仍可通过统一配方表达，但默认零强度。相机响应继续由 JSON + LUT 定义，输入归一化没有实测数据时保持 identity。

所有风格配方当前仍标记 `approximation`。本次没有实体相机配对样张，没有生成或发布实测 LUT，也没有验证 iPhone 画质、帧率或 Swift 编译。合成数据只证明工具工作，不证明还原度。

## 渲染依据与旧约定

- 应用与 macOS 工具共同编译 `modules/camera-engine/ios/CameraProfileRenderer.swift`。
- 同一共享 `CameraEngineGPU.ciContext`；工作空间明确为 extended linear sRGB，沿用原来的默认行为；cube 继续通过 `CIColorCubeWithColorSpace` 指定 sRGB，输出 sRGB。
- `camera18-srgb-ci-v1` 标识现有颜色计算约定，不是“已证明正确”的认证。必须通过原生 identity cube / 灰阶 / RGB 探针验证转换域后，才能用候选 LUT 替代生产响应。不要凭字段名或 CPU 近似判断 gamma 正确。
- tone 仍由原有 Core Image 阶段执行，没有把 CPU 近似曲线烘焙进生产 LUT。
- `tools/look-tuner.html` 只编辑 JSON、比较已渲染图片；不再包含 WebGL 滤镜、另一套颗粒或旧预设副本。

## 配方与 override

每台相机的 `recipe` 包含 version、status、colorContract，可带 datasetId。状态为 approximation / candidate / measured / passthrough。旧 JSON 没有 recipe 仍能导入，诊断显示 legacy/unversioned。

开发校准面板显示文件来源（bundled/override）、每台相机版本、额外颗粒强度及像素参数指纹。指纹用于排错，不是安全校验。既存 override 优先，不自动迁移或覆盖；先导出备份，再使用 Reset Default 才能测试新内置基线。

`raw`、`tone.exposureBias`、`texture.halation/starburst` 是旧导入兼容字段，不参与当前渲染；新内置配方不再包含这些无效参数。不要通过调它们判断效果。`scripts/converge-six-cameras.js` 是旧目录迁移脚本，已停止执行，防止覆盖八模式生产目录。

## 原生自检与图片渲染（macOS）

```bash
bash scripts/native-calibration.sh self-test
bash scripts/native-calibration.sh render \
  assets/camera-profiles.json ricoh_negative \
  modules/camera-engine/ios/LUTs source.jpg rendered.png final
```

脚本编译临时 macOS 可执行程序，用完删除；不签名、不出 iOS 安装包、不触发 CI。没有 macOS 时明确退出，不伪装为 CPU 验证通过。先运行 self-test：检查中性编译、identity cube 的传递函数、deharsh 在预览／照片中的一致性。任何一项失败都停止配方升级，先调查工作空间与输入／输出域。

`render` 输出无损 sRGB PNG，用于对照；不能代表应用 HEIF 编码和真机采集质量。ORIG 只复制原始字节，要求保留原文件扩展名。`preview` 模式使用相同渲染器，但离线图片输入不等于真实视频帧，预览输入偏差仍需真机验证。

## 采集两类证据

1. 受控配对：记录设备／镜头、焦段、光线、曝光、白平衡、目标相机模式和全部自定义设置。对齐构图并选择对应区域，控制这些变量用于比较响应本身。不要在应用里增加手动曝光入口；受控条件在测量环节完成。
2. 日常自动：保留正常自动曝光／白平衡，覆盖肤色、绿植、天空、鲜艳物体、暖光、混合光、高反差、低照度及不同物理镜头，检验实际稳定性。

将图片明确转换为带配置文件的 sRGB，再提取对应色块的平均 RGB；用 0...1 编码值。不可直接拿 P3 数值、线性 RGB、截图或未对齐像素混用。对照图由用户持有，不将私人样张提交到公开仓库。

按完整拍摄场景划分训练／验收集。同一拍摄、同一张图的裁切不能分到两边。至少两个训练场景（合计 24 个色块）、一个独立验收场景（12 个色块）；这是启动门槛，不是充分校准标准。

## 数据格式

```json
{
  "schemaVersion": 1,
  "id": "grit-n-daylight-001",
  "evidence": "paired-camera",
  "colorSpace": "srgb-encoded",
  "source": {"device": "实际 iPhone + 镜头", "settings": "系统版本、焦段、曝光和 WB 记录"},
  "target": {"device": "实际目标相机 + 镜头", "settings": "模式、曝光、WB 及自定义参数记录"},
  "scenes": [
    {
      "id": "daylight-portrait-a",
      "split": "train",
      "lighting": "记录光源与条件",
      "captureIds": ["source-original-file-id", "target-original-file-id"],
      "samples": [{"source": [0.7,0.5,0.4], "target": [0.71,0.51,0.39], "category": "skin"}]
    }
  ]
}
```

上例只展示结构，场景与色块数不足，不能拿来拟合。synthetic 证据必须标记 `evidence: "synthetic"`。

## 生成候选与独立评估

```bash
node scripts/calibrate-camera.js fit dataset.json ricoh_negative calibration-output/grit-n-001
bash scripts/native-calibration.sh probes \
  calibration-output/grit-n-001/profile.json ricoh_negative \
  calibration-output/grit-n-001 calibration-output/grit-n-001/probes.json \
  calibration-output/grit-n-001/native.json final
node scripts/calibrate-camera.js evaluate dataset.json calibration-output/grit-n-001/native.json
```

拟合使用按场景均衡的二次 RGB 残差 + 正则化，采样为 33³ LUT；只拟合训练集，独立统计验收集。它是一个可复现的初始方法，不保证所有相机响应都能被这种低阶模型表达。数据少或效果差时补数据／重新审视目标，不自动加模型复杂度。

输出 profile.json、候选 cube、report.json、probes.json。候选颜色响应只由一个 LUT 承担，其他颜色／影调／质感参数中性化，防止重复处理。工具拒绝覆盖同名输出文件。候选状态始终为 candidate，不自动复制进生产或改成 measured。

报告包括：训练／验收 OKLab 距离均值、P95、最大值、分类误差、基线误差、通道裁切比例、数据指纹。该距离是 OKLab 欧氏距离 ×100，**不是 CIEDE2000**。CPU 三线性采样报告只作拟合诊断，原生 probes 报告才反映该渲染器的颜色输出。二者均不能替代画面和性能验收。

`probes` 为测量颜色而关闭空间颗粒／暗角；完整 render 保留配置。输入探针及顺序必须与数据集匹配，否则拒绝评估。

## 发布条件

- 同一候选在独立场景优于旧响应；肤色／灰阶／高光不能以平均误差下降为由明显退化。
- 查看正常大小与 100%：无新增颗粒、明显色块、颜色断层、异常剪切；允许目标参考本来具有的反差，不用所有模式相同的黑位限制替代审美判断。
- 用同一张原片分别渲染旧／新响应做盲比，另比较目标原片。
- 真机检查真实视频输入与成片差异、HEIF 输出、不同镜头、暖光／混合光、连拍、处理耗时及内存。共享 deharsh 新增预览阶段，必须测帧率与温升。
- 保存数据来源、配置、独立验收报告、原生渲染器版本、LUT 校验和。上述条件完成后才人工升级 measured，并给出新 recipe.version；不要只因为拟合跑完就宣传精确还原。
- 保持快门 promise 与后台处理解耦；不更改光圈／物理镜头路由，不引入假景深、额外专业控制或在线 AI。
